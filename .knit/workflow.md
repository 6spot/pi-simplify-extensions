# 四环节工作流

Knit 以讨论 → 实施 → 检查 → 交付四个环节推进任务。本文件是项目资料：可按项目实际调整职责描述，Knit 只补缺不覆盖。

## 主会话：识别请求与任务入口

主 Agent 按上下文把每轮请求归入一类处理，不按关键词机械建任务。**是否创建 Knit 任务由用户决定**：用户要求创建或已有持续授权时创建；用户明确不创建时直接执行，不因代码修改、调研、委派或报告落盘而强制建任务。普通问答与状态查询直接回答；新事项先问是否建任务再展开需求，对可能形成实施、文档或需要跟踪成果的事项不按请求类型、预估大小或是否使用工具跳过。用户暂不创建时继续讨论，转到实施前再确认；明确不创建时同一事项持续有效，不重复追问。实施前仍无有效任务选择时先补问，不能用“你做吧”代替。

- **不建任务**：普通问答、只读调查、代码审阅、非正式小修改和用户明确不跟踪的修改，都在当前会话直接完成并汇报。只读调查即使需要多轮读取或临时委派，也不创建形式上的任务。
- **委派边界**：不建任务时使用宿主提供的通用工具／子 Agent；Knit 的 `run` 只服务正式任务，不派发无任务 worker。宿主没有可用委派能力时直接执行，并如实说明，不暗建任务冒充支持。
- **新正式需求与需求澄清门**：正式需求可以是代码、文档或研究报告；创建任务前先判断需求是否已足够明确。
  - **关键缺口先讨论**：目标、范围、行为或完成条件任一存在需用户取舍的缺口时，先向用户呈现缺口与可选项并讨论，不得把 Agent 自行补齐的理解写成“已确认要求”后创建待执行任务。已有资料或代码能查清的事实先自行调查，不为查证类问题打扰用户。
  - **需求明确直接登记**：用户已给出目标、范围与完成条件，或唯一合理解释可从资料核实时，直接以简洁提议说明目标与拟建任务；用户已明确要求或已有持续授权时直接 `task new`，不机械追问、不固定多轮。
  - **想法登记**：用户只要登记想法或待讨论时允许建任务，但 task.md 需求区标注“需求未确认，仅登记想法”，保持 discuss 不 ready；phase=discuss 本身不证明需求已确认。
  - **假设标注**：Agent 提出的假设、方案、验收建议写入 task.md 时标注“（Agent 建议，待确认）”；用户确认后才升级为已确认要求，两者不混写。
  - **复杂需求先拆分**：非常复杂的需求先提出多任务拆分方案（各任务边界、依赖、执行顺序、各自交付物与验证），经用户确认范围后逐个登记；每个任务只携带自身必需输入与上游结果，不复制全部讨论；上下文可集中时优先用任务内 plan.md，而非强行拆任务。
  - **创建同意不等于实施授权**：`task new` 征得同意只覆盖登记，不等于需求确认或实施授权。用户明确“按这个做”等可同时确认范围与授权实施，不重复确认；仅认可思路且实施意愿不明时补问，不自行开工。ready 与派发实施仍按既有授权规则，授权不覆盖提交／发布。
- **继续已有任务**：读取当前任务资料与记录接续；已完成授权事项不重复询问。
- **历史查询意愿**：用户明确表达查历史、查上次决定／处理／修改或追溯问题的意愿时，用 `knit task search <查询词...>`（或桥接 `knit_task` 的 `search`）只读检索当前任务、归档、run 记录与 Git，并引用 `path:line`、run ID 或 commit。未表达意愿时不为话题相关主动检索；找到相关记录不等于证明因果，缺少复现、对照或验证证据时要说明缺口。
- **已有任务补充／范围变化**：用 `task update --kind clarify/change` 更新；活动运行期间保存为草案，待运行结束后应用。不默认另建新任务绕过旧任务状态。

正式任务创建时确定完成验证要求：`none`（用户明确跳过）、`self`（实施自检与范围验证，默认）或 `independent`（独立 check）。用户明确要求的验证范围优先；`task verification` 只能在讨论阶段调整。建任务不等于提交／发布授权。

## 讨论 discuss

明确目标、完成条件与范围。讨论先取证后提问：从任务资料和工程代码取事实，已有资料能回答的先自行调查、不重复询问；只就需用户取舍的事项提问，未决定不自行选择。讨论达到可实施时，归纳问题、范围、完成条件与待决事项并写入 task.md 输入区；仍有需用户取舍的事项先澄清，不带着未决问题进入实施。任务创建同意不等于需求确认或实施授权；需求澄清在 discuss 完成，实施授权按既有规则另行确认。

复杂任务（多模块、迁移、协议、跨会话接续）在讨论确认时创建任务目录内的 `plan.md`：写清步骤产出、真实依赖、受影响结构／接口、验证方式与风险处理，保留未完成步骤标记。有重要技术取舍时写 `design.md` 保留备选对比与理由；调查材料多时放 `research/` 并在 task.md 输入引用中留入口摘要。简单任务只在 task.md 说明即可，不堆空文件。

## 规范沉淀

规范是项目事实，不依附任务。任何交流（含无任务讨论）都可沉淀，不为保存规范暗建任务。

- 用户明确长期规则且含义清楚时，直接整理采纳到正式规范并说明替换内容；不重复询问同一决定。
- Agent 判断足够明确时可自行采纳，依据须来自讨论决定、已验证实践或多次一致处理，适用范围清楚；不替用户填补未决目标或偏好。
- 与已有规范冲突时先提出冲突、影响和建议，取得用户决定；未决定不改正式规范。
- 未明确的可复用内容用 `standards propose` 保存为项目级候选（`.knit/standards/candidates.md`），保留来源、建议和待确认点；一次性要求只留本次范围，不提议为通用规则。
- 采纳用 `standards review --decision applied` 记录理由与目标，再由 `standards apply` 写入正式规范并补索引；自行采纳同样记录依据。
- 旧任务 `standards.md` 只读兼容，可按需 `standards migrate` 迁入项目候选；规范处理不阻塞交付，也不重新绑定任务。
- 正常回复末尾简短说明本次沉淀的内容、适用范围和存放位置；需用户决定的问题当场提出。

## 实施 implement

按任务目标与规范完成代码、文档或研究报告等产出，复杂任务按当前 plan.md 的未完成步骤推进。开始前核对输入已冻结；实施在快照就绪后进行。遇到需用户决定的事项记录后暂停，不自行取舍。不要为了产生改动而改无关代码；任务没有可核对产出时明确报告缺少成果。

实施中勾选计划步骤、追加证据是进度更新，不改变需求（主会话可直接写回计划资料；阶段执行器在报告中说明进度，由主会话写回）；要改动目标、条件或验收，必须走 `task update --kind clarify/change`，不能只改计划文件。验证按目标、改动范围、影响与风险选择：小范围只跑相关检查；涉及共享基础设施时按实际影响扩大并说明理由；用户明确要求的更广／更窄范围优先。`self`／`none` 任务的实施获准后进入交付阶段；`independent` 任务进入检查阶段。完成自检后按任务验证要求继续，不宣称未验证的结果。

## 检查 check

仅在任务要求 `independent` 或用户明确要求时执行独立检查：核对 task.md 完成条件与实际成果，运行验证、记录发现。检查按冻结时的需求与资料版本评价，不按计划勾选判定成功。检查发现既定需求内、问题与修复方向明确的缺陷时，可直接修复并运行相关验证；涉及需求解释、取舍、验收变化或扩大范围时不动代码，以 `blocked` 交回主会话。检查者对自身修改的验证属于自检，不表述为另一独立执行者已复核，也不默认追加一轮独立检查。`self` 任务的实施自检不自动升级为独立检查。

## 交付 deliver

主会话接收实施与检查结果，核对实际成果与完成条件、汇总修改与验证并向用户报告；不另启动交付辅助 worker。业务完成与 Git 收尾分开：`task close --outcome completed` 记录业务完成，不要求已有提交；多个任务可以先完成、最后再提交。`deliver` 按任务逐项处理，业务产物和任务资料分开提交，再封存、移动和提交归档；批量收尾仍保留每个任务自己的提交记录。

交付前核对：完成资格有效、无待应用输入、提交范围限定在本次任务。未授权时只生成只读计划，不提交、推送或发布；已有明确授权不重复确认，子进程或 worker 完成不代表提交／推送／发布已获授权。推送／发布始终另行授权。

交付中断时按操作记录核实工具与 Git 实际效果，再决定重试或继续，不假定未完成或已完成。规范候选未审阅不构成交付前置，也不把规范处理重新绑定任务。
